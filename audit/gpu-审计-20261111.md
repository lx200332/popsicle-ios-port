# Adreno 840 GPU 驱动完成度静态审计

审计对象：`/opt/work/ci/buildtree/xnu/bsd/dev/pandora_gpu.c`（166,817 B / 4,085 行）、`pandora_csfw.c`（9,911 B）、`pandora_gpi.c`（13,658 B）、已链接内核 `/opt/work/out42/kernel.development.pandora.unstripped`、`/mnt/d/ios/_work/klogY.txt`、`/mnt/d/ios/_rebuild/boot44.log`。只读审计，未改动任何文件。

## 一、结论

1. **15 级初始化路径在源码和日志上都是"全部打通"的**：klogY 与 boot44 都在 0.251 s 内把 level 2..14 逐条打成 `done`，level 15 在同一时刻由 `gpu_level14(level>=15)` 内部调用完成，没有任何一级 `stopped`——驱动不是"半成品"，它已经能把 Adreno 840 从 CX 上电一路带到用户态 Metal 提交并回读正确结果。
2. **真正的缺口不在初始化而在运行期调度与恢复**：没有真 SMMU 上下文/ASID 切换（15 个 client 共用一张 36 位页表，`pandora_gpu_ctxsw` 只是在换 client 时往 ring 里塞一段上下文入口包）、没有中断驱动的 SMMU 故障处理（`gpu_fault_check` 由 DCVS 线程每 16 ms 轮询一次）、没有 GPU reset/recovery、perfcounter 只有硬件初始化没有读回、ACD/IFPC/抢占全部关掉。
3. **性能差距不是 boot-arg 造成的，而是提交路径与调频驻留**：`pandora_gpu_flushall` 默认 0（日志里 `flushall 0`），`pandora_gpu_perf`/`bw` 默认给最低档但会被 DCVS 覆盖；实测我们每次提交 7–23 个 IB、52–214 µs（黄金 4 个 IB、32–37 µs，慢 2.9×），DCVS 有 11/27 次采样停在 222 MHz（黄金 2/20），最终 315 s 只提交 2334 次而黄金 210 s 提交 18,679 次。

> 需要纠正一个前提：`boot44.log` **不是苹果原厂 GPU 路径**。它含 19,429 行 `PANDORA GPU`、同一份 15 级 banner、同一个 `AGXAccelerator (IOAcceleratorES) registered, plugin NativeAdrenoMetal`，是同一套 pandora 驱动的更早（2026-11-06 20:43）构建。把它当"黄金"只能当"我们自己以前的更好状态"，不能当"苹果实现"来对照功能缺失。

## 三、PMGR 双打印谜题的判断

**结论：这不是 `pandora_gpu.c` 里任何函数体被执行两次。`pandora_gpu_init` 与 `pandora_pmgr_init` 是两个不相干的函数，互相之间没有调用关系；日志里那对自相矛盾的打印来自 `PandoraPMGRNub.cpp` 的发布线程，当前内核二进制在静态上不可能复现它，机制层面无法判定，需要一次实验。**

证据（按强度排序）：

1. **函数归属（强，源码 + 符号表）**：`pandora_pmgr_init` 在 `/opt/work/ci/buildtree/xnu/iokit/Kernel/arm/PandoraPMGRNub.cpp:298`，唯一调用点是 `osfmk/kern/startup.c:720-721`（`extern void pandora_pmgr_init(void); pandora_pmgr_init();`）。`pandora_gpu_init` 在 `pandora_gpu.c:4067`，唯一调用点是 `bsd/dev/sweet_ufs.c:1594`（`extern` 声明在 `sweet_ufs.c:67`），位于 `sweet_ufs_init()` 内。两者无任何交叉引用。
2. **反汇编（强）**：`/tmp/dis.txt` 里 `_pandora_pmgr_init` 只有 **1 个** `bl`：`fffffff007ae1168: bl 0xfffffff007a8b044 <_pandora_pmgr_init>`，宿主函数 `_kernel_bootstrap_thread`（`0xfffffff007ae0ea8`，偏移 +0x2c0）；`_pandora_gpu_init` 也只有 1 个 `bl`：`fffffff007487ab0: bl 0xfffffff0074c4bf0 <_pandora_gpu_init>`，宿主函数 `_sweet_ufs_init`（`0xfffffff0074876ec`，偏移 +0x3c4）。两处各一次。`pandora_pmgr_thread` 只有一个（`__ZL19pandora_pmgr_threadPvi` @`0xfffffff007a8b0bc`），`kernel_thread_start` 在 PandoraPMGRNub.cpp 里只有一处（L306）。
3. **字符串副本数（强）**：当前内核里 `PANDORA PMGR: publisher started`、`PANDORA PMGR: ApplePMGRNub %p published under %s @%s:%d`、`PANDORA PMGR: %s` 各只有 1 份；失败串也只 1 份。同一份 `.text` 里不可能从两个调用点打出成功和失败。
4. **矛盾确实存在（强，日志）**：klog5–klogF 每个文件都同时含成功与失败。以 `klog5.txt` 为例：L57 `[0.128] publisher started (mode 1)`、L77 `[0.136] ApplePMGRNub published (no provider: reads 0xffffffff, writes ignored)`、L78 `[0.136] PANDORA AES: IOAESAccelerator published`、L1671 `[30.413] no ApplePMGRNub class after 30 s`、L1672 `[30.413] PANDORA AES: no IOAESAccelerator class`。单次启动由 1× Darwin banner / 1× iBoot / 1× AMFI policy / 时间戳单调证明。**AES 走的是完全相同的成功→30 s 失败曲线**，两者都出自 `pandora_pmgr_thread`（L242–L295，`pandora_aes_publish(platform)` 在 L294），轮询都是 300×100 ms。
5. **时序（中）**：klog1–4（Nov10 18:06–19:10）纯失败；klog5–F（20:08–22:02）成功+失败；klogG/X/Y（22:26 / 23:53 / Nov11 00:41）纯成功。矛盾的窗口是过渡态，末期已干净。`PandoraPMGRNub.cpp` 与 `startup.c` 的 mtime 都是 2026-11-03 14:21（未再改动）。

**无法判定的部分**：既然当前二进制只有一个调用点、一份字符串，`klog5–klogF` 的双打印只能来自(a) 更早的内核镜像（那两个小时里换过镜像），或(b) 发布线程被 `kernel_thread_start` 启动了两次（需要更早镜像里有第二处 `pandora_pmgr_init`），或(c) 日志是两段串口采集拼接。klog5 的 1× banner 与 152 行普通 UIKit/AKS 重复文本削弱了(c)，但 klogY 本身已经证明这套采集**确实会拼接**（见第五节），所以(c)不能排除。

**需要的实验**：用**当前** `/opt/work/out42/kernel.development.pandora.unstripped` 以 `pandora_pmgr=1` 复跑，看是否两条都出现；再加 `pandora_pmgr=3`（L290 的门限会在成功发布后立刻 panic），能区分"成功路径走过一次"还是"走了两次"。这一步在静态阶段无法替代。

## 四、未实现路径清单

1. **真 SMMU 上下文切换 / ASID 切换——没有。** 全驱动只有两个上下文：GMU（bank 0 / ASID 1 / SID 5 / slot 2）和 GPU（bank 0 / ASID 2 / SID 0 / slot 3，36 位，2048 表页），各建一次。15 个 client 共用同一张页表，靠 `gpu_window_of()` 切成 4 GiB 窗口（`(client+1)<<32`；32 位布局退回 `gpu_window32[]`）。`pandora_gpu_ctxsw` 只决定"换 submitting client 时是否在 ring 前插一段上下文入口包"（`pandora_gpu.c:3084-3090`），没有 CB_TTBR0 换页表、没有 per-client ASID、没有切换时 TLB invalidate。
2. **中断驱动的故障处理——没有。** SMMU 一个 IRQ 都没配（`IRQ_CFG`/`GLOBAL_FAULT`/`sIRQ`/`SCR0` 中断使能全部零命中）；`bsd/dev/adreno/ArmSmmu4K*.c`（834 行）也没有 IRQ 支持。故障检测是 `gpu_fault_check()`（L3783）挂在 DCVS 线程每次唤醒的第一句（16 ms），加 `gpu_watch()`（L3671）每 5 s 一次；只在**事后**读 FSR/FAR/FSYNR0 并打印，不清故障、不恢复。
3. **GPU reset / recovery——没有。** 只有 `gpu_submit` 里 `reset` 分支的 `CP_RESET_CONTEXT_STATE`（per-submission 上下文入口包）和 level 5 里 `GMU_CM3_SYSRESET` 的开关。`grep -i recover` 零命中。
4. **perfcounter 采样 / 性能 API——没有。** 硬件只做了初始化：`RBBM_PERFCTR_CNTL 0x460`、`RBBM_SLICE_PERFCTR_CNTL 0x500`、`CP_PERFCTR_CP_SEL 0x8d0`、`RBBM_PERFCTR_GPU_BUSY_MASKED 0x19e`、`SP_PERFCTR_SHADER_MASK 0xae0f`、`PC_CONTEXT_SWITCH_STABILIZE 0x9e64`；SRAM 复位序列只在 submit 的 reset 块里（`0x449`/`0x5e8` + `CP_WAIT_REG_MEM` 等 `0x19f`）。没有任何计数器回读，ABI 17 个方法（Query=1 … BoImport=16）里没有 perf 方法。
5. **抢占——没有。** `CP_CONTEXT_SWITCH`、`CP_SET_CTXSWITCH_MODE`、preempt 相关寄存器零命中；`CONTEXT_SWITCH` 只以 `PC_CONTEXT_SWITCH_STABILIZE_CNTL_1` 和 `RB_CONTEXT_SWITCH_GMEM_SAVE_RESTORE_ENABLE` 两个位出现。
6. **硬件队列（CreateQueue/CloseQueue）——没有。** ABI 声明 `=11`/`=12`，但 `pandora_gpu_sizes[11]`/`[12]` 都是 `{0xffff,0xffff}`，`method()` 直接 `return kIOReturnUnsupported`；switch 里也没有 case。只有一条 ring。
7. **ACD、IFPC 上电表、GMU 功耗计数器对外——按设计关闭。** 源码自陈：`pandora_gpu.c:57` "ACD and IFPC stay off"；`:3153` "Not done: the GMU power counters and the IFPC power-up list (no IFPC)"。每次提交都用 `CP_SET_MARKER 0x101` 关 IFPC、`0x100` 再打开。
8. **故障后的地址空间隔离——没有。** `SCTLR.HUPCF` 只保证故障终止那一次访问（软件注释 0316），故障本身靠 watch 线程清 FSR，没有把出错 client 摘掉或重建上下文的路径。

## 五、性能可疑点

| 项 | 事实 | 影响 |
|---|---|---|
| `pandora_gpu_flushall` | `gpu_flush_all()` L2881，`on` 默认 **0**；注释记录 bb21：83 个 surface、98 draw 的帧从提交到完成 27 ms。日志 `flushed 0 MiB each (flushall 0)` | **默认不拖慢**。反过来打开它才是灾难（每次提交刷全部 imported 页）。不是当前性能问题的原因 |
| `pandora_gpu_perf` / `pandora_gpu_bw` | level 8 里 `perf=1, bwi=1` → `gpu_opps[1]=160 MHz`、`bw=1`，即**最低档**；但 `gpu_thread` L4038 是 `if (u && !PE_parse_boot_argn("pandora_gpu_perf", &fixed, ...))` 才启动 DCVS | 两个日志都没传这两个 arg，所以 DCVS 在跑，初始档位被 222 MHz 覆盖。**但有陷阱：一旦传 `pandora_gpu_perf=N` 就静默关掉调频器并把频率钉死** |
| `pandora_gpu_perf_max` | 默认 `NGPU-1=18`，实际夹到 1..17 | 不限制 |
| **DCVS 驻留（真凶之一）** | klogY 采样 `now N MHz`：{222:11, 578:4, 902:1, 1200:11}；boot44：{222:2, 1100:1, 1200:17}。同一张 OPP 表、同一个起点 222 MHz | **我们 40% 的采样停在最低档**，黄金只有 10%。busy% 读得低（我们 `busy 8%`）→ 升档条件 `busy_ns*100 > ns*85` 难触发 → 越慢越不升 |
| **提交路径膨胀（真凶之二）** | 每 500 次提交打印：我们 `14/17/19/19/12/23/23/22/7/8 IBs each`、avg 52→214 µs、max 最高 954 µs；黄金稳定 `4 IBs each`、avg 32–37 µs、max 54–71 µs | 单次提交慢 **2.9×**（均值）、最差 **13×**。`gpu_submit` 在 `reset` 时插 10 个包的上下文入口块（4×`CP_WAIT_TIMESTAMP`、`CP_RESET_CONTEXT_STATE`、`LRZ_FLUSH_INVALIDATE`、两个 perfctr SRAM init + `CP_WAIT_REG_MEM`、`CACHE_INVALIDATE`），而 `reset` 由"换 client"启发式触发——backboardd 与画报进程轮流上 ring 时几乎每次都会走全量 reset |
| HFI 积压 | 我们 799 条 `HFI response` 只有 668 个不同 id，**131 个重复**（全 err 0）；黄金 304 条 304 个不同，0 重复。`hfi_send` 的排空循环（L1204）会把过期 seq 的响应也打出来 | GMU 应答偏晚，队列有积压；不是错误路径，但是延迟信号 |
| 中断/fence 速率 | 我们 `[40.287] state 2, 12 interrupts`；黄金同时刻 `1337 interrupts`。末期我们 `fence 4329` 对 `submit 2334`（每 job 等 1.85 个 fence），`rbbm 00000001`（采样时 GPU 空闲）；黄金 `fence 18682/submit 18679`、`rbbm 00ec74a5`（有挂起位） | 中断路径是通的，但吞吐差 8× |
| **`pandora_gpu_bo_alloc` 的 41 次 ENOMEM** | klogY 41 条 `PANDORA GPU UC: client 0 method 2 in 16 out 8 -> 0xe00002bd`，黄金 0 条。池 657/1024 MiB、活跃 BO 88 个、`GPU_MAX_BOS 4096`、`pool extent list full` 0 条 | 不是泄漏、不是槽位、不是 512 extent 溢出，而是 **1 GiB 池在 best-fit 下的碎片**：`align_log2` 最大 24（16 MiB）的请求找不到任何单个 extent。每次失败都是一次 Metal 分配重试，直接进帧时间 |
| `probe a..k` 残留 | level 5 内联 poll 打 28 行 `probe k` + 10 行 a..j，无条件（不是 boot-arg 门控），黄金 0 行 | 14 ms 启动期 + 每启动 38 行日志噪声 |
| `gpu_step` 慢模式 | `pandora_gpu_slow` 默认 0（patch 0183 已把 3.5 s×27 步的老默认去掉） | 不拖慢 |
| `gpu_watch` 开销 | 每 5 s 遍历全部 4096 个 BO 算映射/pool 占用（L3679 起），持 `gpu_lock` | 稳态开销，日志里没体现为热点，但和 `bo_alloc/free` 抢同一把锁 |

## 六、无法验证项

1. **PMGR 双打印的真实机制**：静态可证明"不是 `pandora_gpu.c` 的函数体跑两次""当前二进制不可能两个调用点各打一次"，但无法证明 klog5–klogF 用的是哪个镜像、是否拼接。需要 §三 的实验。
2. **`klogY` 是拼接过的高负载段**：三处独立断点落在同一 500 行窗口——L19488 时间戳 `186.333 → 224.680`（+38.3 s）；L19592 HFI seq `0x1d31031e → 0x1511031e`（回退）；L19989 `5000 submissions → 2500 submissions`（计数器重置）。但 **1× Darwin banner / 1× iBoot / 1× GPU level banner / 1× `interrupt on` / 1× `DCVS: on`**——说明拼的是同一次启动的**两条串口/日志流**（内核 printf 与用户态日志分开抓），不是两次启动。后果：8402 行 GPU 打印**低估**了单次连续运行的总量，任何"每次启动总计数"只能分段读。`boot44.log` 零断点。
3. **`boot44.log` 的身份**：含 19,429 行 `PANDORA GPU`、同一份 15 级 banner、同一个 `AGXAccelerator (IOAcceleratorES) registered, plugin NativeAdrenoMetal` ⇒ 它是同一套 pandora 驱动的更早构建（2026-11-06），**不是苹果原厂路径**。因此"黄金有我们没有"的对照只能说明"我们自己退化了什么"，不能说明"苹果实现了什么"。
4. **golden-only 打印模板**：模板集合差集只有 4 条，全部是串口行交错（`PANDORA BT: pins …` 与 `PANDORA GPU: GPUCC …` 粘成一行）或归一化把数字形状算错。**没有任何 GPU 打印是黄金有而我们没有的。**
5. **`klogY` 缺三个子系统的输出**：`PANDORA THERMAL` 0 行（boot44 98 行，含 `7 controllers, 6 groups`、`max 111.4 C (warn)`）、`PANDORA BT` 0 行（boot44 10）、`PANDORA MODEM` 0 行（boot44 5），而 `PANDORA CPU` 两边都是 80 行、`ADSP` 32/34、`FILES` 1/1、`IDLE` 2/2。boot-args 两边都带 `pandora_thermal=1 pandora_bt=7`（klogY 还多 `pandora_thermal_test=40`）。同一 `sweet_ufs_init()` 里 CPU/GPU/THERMAL/BT/MODEM 是顺序调用的，前两者有输出、后三者没有 ⇒ Nov-11 那份镜像在这三个 init 上出了问题（或日志过滤掉了），**静态无法判断是哪一种**。这直接影响 `pandora_thermal_gpucap` 是否真的在 klogY 里生效——thermal 线程没输出，就无法证明温度封顶在起作用。
6. **41 次 ENOMEM 的确切对齐需求**：只能说"碎片 + 大对齐"，因为失败行里没有 `align_log2` 与 `bytes`（ABI 只回 8 字节）。要定位得给 `pandora_gpu_bo_alloc` 的失败分支加一条带参打印。
7. **`gpu_pool` 的物理连续性**：`pandora_gpu_init` 在 launchd 之前调 `gpu_pool_reserve()`（level ≥13），代码注释说取到 1 GiB，日志 WATCH 显示 1024 MiB 可用；但 `gpu_pool_carved` 走的是 ADT `pandora-gpu-pool` 保留内存还是运行时 `ml_io_map_unmappable`，两日志都没有明确一行，无法从日志判定。
8. **boost 阈值/上限的实际效果**：`DCVS_BOOST_MIN_HZ=578 MHz`、`DCVS_BOOST_NS=50 ms`、`DCVS_IDLE_NS=80 ms`、`DCVS_CEILING_NS=50 ms`、down-step 需 `4+hold` 次 —— 数值已读实，但哪个条件在我们这边不满足（busy 采样偏、还是 16 ms 窗口太短）需要带计数器导出的实验，不能静态定论。
