## 二、地址层：45/45 命中真机 DTS（零缺陷）

解析 `popsicle_merged.dtb`（1,723,024 B → 925 节点 / 1,124 个 reg 区间，按 `#address-cells`/`#size-cells` 自上而下继承），45 个真实 MMIO 基址**全部落在 DTS 窗口内**。此前怀疑的几处全部排除：

- **TLMM `0x0f100000`** = `pinctrl@f000000`（`reg=<0xf000000 0x202000>`）+ `0x100000`。这是 downstream `pinctrl-canoe.ko` 的约定，**代码正确**。用 `0x0f0xxxxx` 会挂总线。项目文档 `夜间进度.md:12` 写"实锤 0x0f000000"是错的。
- `AD_RSC_PA 0x18920000` 是 `rsc@18900000` 的第三段 reg。
- `AD_MUTEX_PA 0x01f43000` 是 `syscon@1f40000` 跨 stride 0x1000 的第 3 把锁。
- `GMU_PA 0x3d37000` 是 `qcom,kgsl-3d0@3d00000` 的 `+0x37000`。
- `MD_MEM_PA 0x8aa00000` 与 `modem.mdt` 的 `ph1 paddr=0x8aa00000 … ph7 paddr=0x8b070000` 逐条相符。

## 四、六个必须修正的真缺陷

### D1（已修）`pandora_touch` 与 `popsicle_syna` 抢同一组硬件 —— cmdline 冲突
两者**同一颗芯片、同一条 SPI SE `0x1a80000`、同 5 个 GPIO（48/49/50/51/158/66/117）、同一 iovdd `L4I_E0`**，reset / avdd / SE init 动作逐项相同。同时使能时后启动者会 reset 芯片并打断先启动者的会话，两个线程还会同时读写同一 SE 的 FIFO。
**已处置：`boot-drv8.img` 的 cmdline 删掉 `syna=1`**（保留 `pandora_touch=0xf` + `touchscreen=1`，后者是背屏 goodix 的 GPIO 12-15/201/185/82，不冲突）。

### D2（待修）`pandora_sensors=1` 等 6 个门禁加不进 cmdline
605 B 上限 608，**只剩 3 字节**。`boot-drv8.img` 已通过删除 `amfi_get_out_of_my_way=1`（0337 接管后无读者）、`pandora_thermal_test=40`（仅 cpu 自测）、`syna=1`（D1）腾出 41 B，塞进 `pandora_amp=1 pandora_usb=1 pandora_therm=1 pandora_sensors=1 pandora_selftest=1`（593 B，余 14）。

### D3（待修）`pandora_mem.c` 违反作者意图被接进产线
作者头注释原文：`NOT REGISTERED IN bsd/conf/files -- deliberately. … wiring it into the real build (and calling pandora_mem_init() from sweet_ufs.c) is a separate, reviewed change.` 但 `conf/files:150` 注册了、`sweet_ufs.c` 也调了。**要么撤掉，要么补一次 review。**

### D4（设计如此，但要写进文档）`redwood_input` 队列零消费者
`/dev/redwood-touch`（0666）建成、512 深队列、6 个 `redwood_touch_post` 调用点（`popsicle_syna.c:1294/1336/1338`、`popsicle_goodix.c:871/873/883`），**全盘无 open/read 消费者**，代码自己注释 `/* nobody reads: drop the oldest */`。它与 HID 链无关（HID 走 `sweet_hid_touch` → `SweetHID.cpp:577`）。

### D5（待修）`sweet_touch.c` 是编译期死代码
调用点 `sweet_ufs.c:1628` 落在 `#if defined(FUXI)` 的 `#else` 分支，PANDORA 构建永不编译。21,152 B 的驱动 + 27 条 `SWEET TOUCH:` 字符串在镜像里但永远不跑。

### D6（认知纠正）三个"死入口"是假阳性
`pandora_scanout_init`（`SweetFramebuffer.cpp:1532` 调）、`sweet_spmi_init`（`SweetBattery.cpp:385` 调）、`pandora_pmgr_init`（`startup.c:721` 调）**都有调用者**。`grep -w` 判死会漏掉 C 符号的前导下划线。

## 五、三个已关闭的历史谜题

| 谜题 | 结论 |
|---|---|
| **PMGR 双打印**（`published` 0.136 s + `no ApplePMGRNub class` 30.413 s 同一次 boot） | **两个不同 boot 的日志混读**。扫描 20 份 klog：成功进桌面的 klogG/X/Y `fail30 = 0`；只有 `initproc failed` → `restart type 4` 整机复位的那 20 份（klog5–F、klog/klog2/3/4）才有 `[30.413]`，因为第二次 boot 复用同一个 4 MiB 日志环。klogY 时间戳单调性 **0 次回退**。`pandora_pmgr_init` 全内核唯一调用者，反汇编只有 1 个 `bl`。**PMGR 无缺陷，关闭。** |
| **DPU 色彩错** | 不是 DPU：彩条诊断镜像（loader 直接写面板内存）证明面板通路就是 **BGRA8888，一字节不差**，中带/下带的 10-bit 打包显示结果与预期完全对应。真因是 rootfs 缺 `com.apple.backboardd.plist`（`CAEnableDeepFramebuffer=False`），CA 选了 `b3a8`（RGB10A8_2P_XR10 双平面）而 `present()` 原样 memcpy 给 8 位面板。**补 plist 后用户确认"颜色也正常了"。** |
| **GPU 卡在 `release CM3 reset`** | 不是 GMU 挂死。probe 插桩证明 `gmu_wr(SYSRESET,0)` 与随后 `gmu_rd` 都成功，线程死在 `gpu_poll` 的 t=9500；同一时刻 AMFI 报 `code signature validation failed` → `initproc failed` → `restart type 4`，**线程是被整机复位干掉的**。根因是 trust cache 少 7 条 cdhash（模块0 2762 vs 2760、模块1 98 vs 93）。 |

## 六、GPU 的真实完成度（`aud-gpu` 独立审计）

**15 级全部打通**，0.251 s 内 L2→L14 逐条 `done`，无一级 `stopped`——不是半成品。

**未实现的 6 项**：真 SMMU ctxsw/ASID（15 个 client 共用一张 36 位页表，ctxsw 只是换 client 时插上下文入口包）、中断驱动故障处理（`gpu_fault_check` 靠 DCVS 每 16 ms 轮询，无 SMMU IRQ）、reset/recovery、perfcounter（只初始化无读回）、ACD/IFPC/抢占、`CreateQueue`/`CloseQueue` 直接 Unsupported。

**性能真凶（两条，都不是 `flushall`）**：
1. **DCVS 采样停在 222 MHz**（我们 11/27 次，黄金 2/20）——`pandora_gpu_perf` 传了会静默关掉 DCVS，别传；
2. **提交慢 2.9×**：7–23 IB / 52–214 µs vs 黄金 4 IB / 32–37 µs，最差 13×，因为换 client 触发全量 reset 块。315 s 提交 2,334 次 vs 黄金 210 s 18,679 次。

**打印密度 2.31× 差距 98% 是 WPTR**（黄金提交 4× 更多作业），不是我们打了多余的日志；**黄金没有任何我们没有的 GPU 打印**。

**前提纠正**：`boot44.log` **不是苹果原厂**，是同一套 pandora 驱动 2026-11-06 的更早构建（19,429 行 `PANDORA GPU` + 同一份 15 级 banner + 同一个 `AGXAccelerator … plugin NativeAdrenoMetal`），只能当"我们自己以前更好"。

## 七、WiFi：`fuxi_wlan.c` 不是完整驱动（`aud-wifi-pcie` 独立审计）

105 KB 的 `fuxi_wlan.c` 只做到"寄存器级前半程"：ATU outbound×2、BAR0 sizing、LTSSM、PERST 时序、GCC/ICC/RPMh 投票、SID CRC8 全有，**但 13 个窗口全用 SM8550 地址**：

| 项 | 驱动里的值 | 真机 DTS |
|---|---|---|
| DBI 窗口 | `0x60000000` | `0x4_00000000` |
| PERST 引脚 | gpio **94** | gpio **102** |
| WLAN_EN | gpio 80 | gpio 16 |
| RPMh | `0x17a20000` | `0x18920000` |
| PHY 表 | 109 对 | DT 199 三元组，**仅 1 对重合** |

**枚举不出 `cnss_pci0`**：全树 `IOPCI*` 符号 = **0**、`conf/files` 无 `pci` 行、驱动无 `registerService`/`IOService` 子类。当前 cmdline 下 `:2441` 直接 return，**121 处 printf 一行不出**；`popsicle_wifi` 打 106 行只读 survey。

`popsicle_wifi.c` 的定位是纯 survey（源码自述 "Reads only"），ELBI `0x4_00000f20` 与真机 DT **一致**（比 fuxi_wlan 准），与 fuxi_wlan 互补不重复。

**缺口 16 项**，最重三项：① PCI 总线枚举框架（全树 0，需新写）② 真机地址映射（改常量）③ PERST/WLAN_EN 引脚（TLMM 窗口只覆盖 gpio76..99，gpio102/104 连读都读不到）。

## 八、做不到的四类（不是"还没做"，是"树内没有依赖"）

| 项 | 为什么做不到 |
|---|---|
| **传感器 6 类在内核驱动** | DTS 零节点（15 个 vendor 前缀全 0 命中）；树内零 I2C 控制器；真机传感器在 **SSC** = ADSP 固件 + userspace（`sscrpcd`/`multihal`/5 个 hals.conf 的 so）；XNU 侧零 `sns_` 客户端。等于把 Android sensors HAL 整套 GPR 协议搬进内核 |
| **指纹出数据** | 无 SPI 子节点（4 个 `spi@` 被 ir-spi/GT9615/spi_cnss/syna TCM 占满）；无 GENI SPI 控制器；goodix/OV 系指纹协议与固件下发流程仓库零证据。只能停在读 GPIO99/56 |
| **相机真实成像** | CCI 寄存器映射缺失；4 个 sensor 的 chip-id 偏移全缺；**s1/s2 根本不在 CCI 上而在 AP GENI I2C**（源码把四个都写成 `cci=0`，是错的）；树内零 CAMSS/ISP |
| **音频出声** | ADSP 从未 ready（pack 只有 3 个 GPU 文件，日志逐条 `adsp_dtb.mdt missing in the pack` → `DTB image failed 2` → `adsp.mdt missing` → `main image failed 2`）；无 GENI I2C master；TDM0 无 controller 节点、无 IRQ；无 LPASS DMA |

**DTS 事实修正**：源码注释说"26 个 `i2c@` 只有 `i2c@a8c000` 有子设备"——实测是 **28 个、8 个有子设备**，其中 `i2c@880000`/`i2c@884000` 挂相机 sensor、`i2c@1980000` 挂 Cirrus 功放三件套、`i2c@a94000` 挂电量计、`i2c@1a88000` 挂 nq@28、`i2c@1a8c000` 挂 nu1671/sc96281。
