## 一、结论

1. **不是完整驱动。** `fuxi_wlan.c` 只做到 DesignWare PCIe 主控的"寄存器级前半程"——iATU outbound 两条 region、BAR0 sizing/赋值、LTSSM 使能与轮询、PERST 时序、GCC/GDSC/ICC/RPMh 投票、SID CRC8 路由——但**全部使用 SM8550 的地址与引脚**（DBI 0x60000000、PERST gpio94、RPMh 0x17a20000），而真机 canoe 的 DBI 在 `0x4_00000000`、PERST 在 **gpio102**、RPMh 在 `0x18920000`。
2. **枚举不出 `cnss_pci0`。** 全树没有任何 PCI 家族代码（`IOPCIDevice`/`IOPCIBridge` 符号数 = 0，`conf/files` 里 `grep -n pci` 为空），`fuxi_wlan` 自己也没有 `registerService`/nub/`IOService` 子类，只做到"读寄存器 + `printf`"。
3. **当前 cmdline 下 `fuxi_wlan` 一行都不打印**，`popsicle_wifi` 会打印约 **106 行**只读 survey 后退出——但这一预测是代码推断，因为 18 份 klog 对两个驱动的命中数全为 0，且 klogY 早于当前内核。

## 三、popsicle_wifi.c 定位

**它是什么**：一个**纯只读 survey 驱动**（标题自称 "FastConnect 7900 (ath12k family) survey driver"）。它的唯一目的不是让 WiFi 工作，而是把"这颗 SoC 上 WiFi 相关硬件现在是什么状态"打成日志，供后续开发取基线。

- 能力边界（源码自述，`:1`–`83` 头注释）：`Reads only -- the single exception is step 0, the optional power-on, which sits behind a *second* boot-arg (wifi_poweron=1, default 0)`。
- 它自己列的"还缺什么"与顺序：① link training（`qcom,pcie-phy-sequence`，"without it the endpoint never answers"）② clocks and resets（`resets = <&gcc 6 &gcc 9>`，pipe/aux/slv clocks，"none of those are voted here"）③ regulators（VDDA_PCIE_0P9/1P2 = S7F0，"RPMh-owned"）④ enumeration ⑤ SMMU ⑥ firmware。原文：`Steps 1-3 above are the blockers; 4-6 come after them and are not attempted.`
- 实际做的事（`wifi_thread` `:335`–`371`）：
  1. `ml_io_map_unmappable` 映射 5 个窗口：TLMM `0x0f100000`/`0xce000`、PARF `0x01c00000`/`0x3000`、PHY `0x01c06000`/`0x2000`、**ELBI `0x4_00000f20`/`0xa8`**、PCIe SM `0x01d07000`/`0x7000`；
  2. （仅 `wifi_poweron=1`）`wifi_power_on_pin`（`:198`）写 gpio16/gpio18 的 cfg/io 并回读比对，`delay_for_interval(2000, NSEC_PER_USEC)`；
  3. `wifi_step1_pins`（`:239`）读 gpio16/18/204/205 的 cfg/level（**只读**）；
  4. `wifi_step2_pcie`（`:254`）读 PARF +0x0/+0x4/+0x8；
  5. `wifi_step2b_parf_dump`（`:269`）raw dump PARF 0x00..0x7c 共 32 字，注释明写 "link-status/device-id semantics NOT decoded"；
  6. `wifi_step2c_link`（`:288`）读 `PARF+0x414` bit7（PHY READY）、`pcie_sm+0x1090`（`qcom,pcie-sm-start-offset`）、`+0x1000`（branch-offset）、`0x1040 + i*8` 共 14 字（`qcom,pcie-sm-debug`）；
  7. `wifi_step2d_elbi`（`:322`）raw dump ELBI 0xa8 = 42 字；
  8. 打印 `survey done (...)` 并 `thread_terminate`。
- **无** IOPCIDevice、无 BAR、无 iATU、无 ATU、无任何 link-training 写、无 MSI、无 SMMU 编程、无固件下载。
- 入口 `popsicle_wifi_init`（`:378`–`392`）：`PE_parse_boot_argn("wifi_probe")` 缺失或为 0 → 直接 return；再读 `wifi_poweron`；`kernel_thread_start(wifi_thread, NULL, &thread)`。调用点 `sweet_ufs.c:1606`（PANDORA 分支内，`fuxi_wlan_init()` 在 `:1622`）。

**和 fuxi_wlan 的关系：定位互补、地址空间重叠、机制互不相干。**

| | popsicle_wifi.c | fuxi_wlan.c |
|---|---|---|
| 定位 | 只读取基线（survey） | 上电 + 尝试 bring-up（milestone 4/5/6） |
| 映射机制 | `ml_io_map_unmappable(..., VM_WIMG_IO)`（永久，unmap 会 panic） | `kmem_alloc(KMA_VAONLY\|KMA_KOBJECT\|KMA_NOPAGEWAIT)` + 逐页 `pmap_enter_options_addr(..., VM_WIMG_IO, ...)` |
| 线程 | 独立 `kernel_thread`，跑完退出 | 独立 `kernel_thread`，`fw_run(limit)` 后退出 |
| 写入 | 仅 `wifi_poweron=1` 时写 gpio16/18 | 大量写（GCC/PARF/PHY/DBI/EPCFG/SMMU） |

**两者都碰 `pcie@1c00000`，且基址重叠：**

| 窗口 | popsicle_wifi.c | fuxi_wlan.c | 冲突 |
|---|---|---|---|
| PARF `0x01c00000` | `0x3000`（`:99`–`:100`） | 与 QMP PHY 合并为 `0x8000`（`fw_windows[3]`，`:89`） | 同 PA 两个 VA 别名，MMIO 语义下共存；fuxi 会写、popsicle 只读 |
| QMP PHY `0x01c06000` | `0x2000`（`:113`–`:114`） | 含在上面 `0x8000` 内 | 同上 |
| TLMM | `0x0f100000`/`0xce000`（`:95`/`:98`，覆盖 pin 0..204） | `0x0f14c000`/`0x18000`（`fw_windows[7]`，`:93`，**只覆盖 gpio76..99**） | 部分重叠；popsicle 能读 gpio16/18/204/205，**fuxi 读不到它们** |
| ELBI | **`0x4_00000f20`/`0xa8`（真机 canoe 地址，与 DT 一致）** | 无独立 ELBI，走 `0x60000000`（SM8550 地址） | 地址体系不同 |
| PCIe SM `0x01d07000`/`0x7000` | 有 | 无 | — |
| DBI/config/BAR0 `0x60000000`/`0x60100000`/`0x60300000`/`0x60400000` | 无 | 有（全部 SM8550 地址，真机 DT **UNCOVERED**） | — |

> 注：`fuxi_wlan.c:93` 的窗口注释写 `TLMM tiles gpio76..96`，但 `0x18000` = 24 页实际覆盖 **gpio76..99**（注释与 size 不一致，但不影响结论：真机 PERST/WLAN_EN 都在窗口外）。

→ **结论：不重复（职责不同），但共享同一块硬件且引脚/地址置信度不一致。** popsicle_wifi 的 ELBI 地址是对的，fuxi_wlan 的 DBI/config 地址是错的；`sweet_ufs.c` 里两者相隔 16 行被接连启动，两个线程异步并发，若将来加上 `fuxiwlan=` 就会同时对 PARF/TLMM 发力（fuxi 写、popsicle 读），日志会互相污染。

### 4.1 `fuxiwlan*` 全表与门禁语义

主门禁（`fuxi_wlan.c:2441`）：

```c
if (!PE_parse_boot_argn("fuxiwlan", &arg, sizeof(arg)) || arg <= 0) { return; }
unsigned limit = (arg == 1 || arg > (int)WL5_STEPS) ? WL5_STEPS : (unsigned)arg;  /* :2443 */
```

语义三层：**① 参数不存在 → return；② 参数存在但 ≤0 → 也 return（短路 `||`，不是"缺省才拦"）；③ `1` 被特殊化成 28（=跑满），`2..27` 是 bisect 到第 N 步。** 因此 `fuxiwlan=1` 与 `fuxiwlan=28` 完全等价，`fuxiwlan=0`/`-1` 与不给参数等价。

| 49–62 | `pcie_sm[0x1040] = …` … `pcie_sm[0x1098] = …`（14 行，步长 8） |

**不会出现**：`step0 power-on requested (wifi_poweron=1): ...`、`power-on wlan-en (gpio16) before ...`、`... writing io=0x%x then cfg=0x%08x`、`... after cfg=0x%08x io=0x%08x OK|MISMATCH`（全部由 `wifi_poweron` 门禁），以及 `-- plus the announced gpio16/gpio18 power-on writes` 这个变体。

若 5 个 `ml_io_map_unmappable` 有任一返回 0，则只有 1 行 `popsicle_wifi: cannot map TLMM/PCIe: ...` 然后线程退出——按 DT 覆盖情况（PARF/PHY/SM/TLMM/ELBI 均存在）应不会发生。

### 4.4 交叉验证：为什么这是"预测"而不是"观测"

- 全部 18 份 klog（`klog.txt` … `klogY.txt`）对 `popsicle_wifi` 与 `FUXI WLAN` 的命中数**均为 0**；
- `klogY.txt` mtime **2026-11-11 00:41:00**，而 `popsicle_wifi.c` 是 **04:03:15**、当前内核与 `boot-drv5.img` 是 **04:47/04:48** → **klogY 早于当前构建，不可能包含当前 popsicle_wifi 的输出**；
- 但两个驱动确实链进了当前内核：`llvm-nm-18` 给出 `_fuxi_wlan_init` @ `0xfffffff0074ed330`、`_fw_run` @ `0xfffffff0074edaac`、`_fw_thread` @ `0xfffffff0074ed8a8`、`_popsicle_wifi_init` @ `0xfffffff007acb43c`、`_wifi_thread` @ `0xfffffff007acb4d0`；内核 strings 里 `popsicle_wifi` 出现 22 次、`FUXI WLAN:` 格式串齐全。

## 六、无法验证项

1. **当前内核从未启动过。** `klogY.txt`（00:41）早于 `popsicle_wifi.c`（04:03）与内核/`boot-drv5.img`（04:47/04:48）；18 份 klog 全无 `popsicle`/`FUXI WLAN` 命中。§四 的 106 行是**代码推断**，不是实测。
2. **canoe 的 `0x60000000`/`0x60100000`/`0x60300000`/`0x60400000` 是否真的不译码。** DT 未覆盖只是软件证据；需真机访问一次看是否 SError（若译码成别的东西，`fuxi_wlan` 会写到未知寄存器）。
3. **真机 RPMh `drv@2` 的 `qcom,tcs-offset`** 在 `canoe_base.dts` 里被 dtc 渲染成 `"", "", "\r"`，需真机读 `0x18920000` 区确认。
4. **cmd-db 内容**（magic `0x0c0330db` + 10 个资源名 + 8 个期望地址）——需真机读 `0x81c60000`。若不符，`wlan.c` case 1 直接 `return 1`，整条链路在第一步就断。
5. **`qcom,qsmmu-v500` 的 impl0 寄存器语义**，以及该 SMMU 当前是否已被 UFS/ADSP/DPU 部分占用（`0x15000000` 的读者至少 8 个文件）。本地 Linux 树无该 compatible 条目。
6. **端点 device id**：代码一律用 `0x110e17cb`（即 `17cb:110e`），而 `fuxi_wlan.c:25` 注释写 `endpoint 17cb:1107` —— 二者矛盾，需真机确证。
7. **`amss20.bin`/`bdwlan.elf` 缺失**，无法验证 `wl_read_firmware` 与 BHI/BHIe 下载路径。
8. **PCIe CRM / PDC 寄存器语义** —— DT 只给 compatible，无公开寄存器定义。
9. **`fuxi_wlan.c:25` 自述 "it passed on the phone (Gen2 x2 link, endpoint 17cb:1107, BAR0 64-bit non-prefetchable 2 MiB)"** 无法核实：该文件 mtime 是 2026-11-03，早于当前内核；且它引用的 `docs-lanes/wlan-bt.md` 在本机**不存在**（`docs-lanes/` 目录缺失）。
10. **在 iOS 内核里注册 PCI 家族的可行性**（是否要改 `IOCatalogue`/`IOPlatformExpert` 的匹配路径）——未评估，工作量未知。
