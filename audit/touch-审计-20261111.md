## 一、结论

1. **四套驱动全部编进内核（`bsd/conf/files` 全部标 `standard`，符号与 banner 字符串齐在），但 `klogY` 那次启动只有 `pandora_touch.c` 真的在跑**——1,942 条 `SWEET HID` 里 1,924 条 touch 事件全部由它的 `pt_deliver()` 产生，源头是 TouchComm THP 帧的峰值计算而非固件触摸报告（三次周期统计都是 `0 touch`）。
2. **`popsicle_goodix` 是背屏（976×596，指纹屏），`popsicle_syna` 是主屏（1200×2608）**——DTS 四重互证：`goodix,panel-max-x/y = 97600/59600`、pinctrl 用 `mi_ts_spi_*_second` 组、avdd 是 `touch_avdd_vreg_second`（GPIO 82）；syna 反之（`syna,touch-type="primary"`、`mi_ts_spi_*` 主屏组、`touch_avdd_vreg` GPIO 117）。
3. **真正会打架的只有 pandora 与 syna（同一块屏、同一条 SPI SE `0x1a80000`、同一组 GPIO 48-51/158/66/117）**；本次没打起来是因为 `klogY` 用的内核（推断 out39）里 `sweet_ufs_init` 根本没 `bl` 到 syna/goodix/redwood —— out40 才接入，而 `sweet_touch.c` 在所有版本里都因落在 `#if defined(FUXI)` 的 `#else` 分支而**编译期不可达**；`/dev/redwood-touch` 队列有生产者、有 512 深度、无任何消费者。

## 三、冲突分析（逐对）

### 3.1 fuxi vs pandora —— **不冲突**

| 维度 | fuxi | pandora |
|---|---|---|
| 总线 | I2C，SE `0x00a90000`（QUP1 SE4） | SPI，SE `0x01a80000`（QUPv3 wrap4 SE0） |
| GPII | 0（`0x00a10000`） | 1（`0x01a14000`） |
| 中断 GPIO | 25 | 158 |
| 复位 GPIO | 24 | 66 |
| 电源 GPIO | 无（loader 投票 ldb12/ldom6） | 117（`touch_avdd_vreg`） |

结论：总线、SE、GPII、四个 GPIO 全部不同，物理上不可能互抢。且 fuxi 在 PANDORA 构建里默认 `enabled=0`，日志实证 `FUXI TOUCH: disabled`（L174）。即使 `fuxitouch=1` 也不会打断 pandora——但会拿 SM8550 的地址表去操作 SM8850 的 QUP1 SE4，属于"无害但无意义"。

### 3.2 syna vs goodix —— **不冲突（引脚层面），但共享控制器与 RPMh 命令通道**

| 维度 | syna（主屏） | goodix（背屏） |
|---|---|---|
| SE | `0x1a80000`（qupv3_4 wrap4 SE0） | `0x1988000`（qupv3_3，SE2） |
| SPI 引脚 | GPIO 48/49/50/51（`qup4_se0_l0..l3`） | GPIO 12/13/14/15（`qup3_se2_l0..l3`） |
| 中断 | GPIO 158 | GPIO 201 |
| 复位 | GPIO 66 | GPIO 185 |
| avdd | GPIO 117（`touch_avdd_vreg`） | GPIO 82（`touch_avdd_vreg_second`） |
| iovdd | RPMh LDO `L4I_E0` 1.8 V | RPMh VRM `L2F_E0` 1.2 V |
| DTS pinctrl 组 | `mi_ts_spi_{mosi,miso,clk,cs}_active` | `mi_ts_spi_{mosi,miso,clk,cs}_active_second` |

**共享项（都指向同一颗 SoC 模块，但按不同寄存器位操作）**：
- TLMM 控制器基址 `0x0f100000`（`pinctrl@f000000` + 0x100000 偏移，四套驱动口径一致；0x0f0xxxxx 会 hang 总线）
- GCC `0x00100000`，三个驱动都读改写同一个 `GCC_CBCR = gcc + 0x52018`，但**位段不重叠**：syna bit 22/23/24（M_AHB/S_AHB/core，halt `0x23548/0x2354c/0x23550`）+ bit 26（SE0，halt `0xa9004`），SE0 RCG `0xa9010`；goodix bit 8/9/10/11（M_AHB/S_AHB/core/core_2x，halt `0x233f0/0x233f4/0x233f8/0x2340c`）+ bit 14（SE2，halt `0xa827c`），SE2 RCG `0xa828c`。两边都是 `rd(GCC_CBCR) | VOTE`（syna L400/L430、goodix L349/L379），RMW 不会清掉对方的位
- RPMh/RSC 命令通道 `0x18920000`：syna 投 `L4I_E0`（cmd-db `0x40d00` slave 4），goodix 投 `L2F_E0`；两者都用 `TSC(reg) = rsc + 0xd00 + reg` 的同一套 TCS 槽位

结论：**引脚与总线不冲突**，可以同时使能（这正是 `syna=1 touchscreen=1` 的设计意图）。唯一残余风险是 RSC 的 ACTIVE TCS 槽争用——日志显示 pandora 占 TCS0、TCS1/2 空闲，若 syna 与 goodix 各自再抢 ACTIVE 集合，需要三者的 tcs-offset 互不重叠。源码里没有对这一点做交叉校验。

### 3.3 pandora vs syna —— **严重冲突（同一个硬件资源组）**

| 维度 | pandora | syna | 是否相同 |
|---|---|---|---|
| 目标芯片 | Synaptics S3910P（TouchComm v1） | Synaptics TCM | **同一颗** |
| 面板 | 1200×2608 | 1200×2608 | 相同 |
| SPI SE | `0x01a80000` | `0x1a80000` | **完全相同** |
| MISO/MOSI/CLK/CS | GPIO 48/49/50/51 | GPIO 48/49/50/51 | **完全相同** |
| 中断 | GPIO 158（轮询） | GPIO 158（轮询） | **完全相同** |
| 复位 | GPIO 66 | GPIO 66 | **完全相同** |
| avdd | GPIO 117 | GPIO 117 | **完全相同** |
| iovdd | RPMh `L4I_E0` 1.8 V | RPMh `L4I_E0` 1.8 V | **完全相同** |
| RSC / cmd-db | `0x18920000` / `0x81c60000` | 同 | 相同 |
| GCC `0x52018` 投的位 | `GCC_VOTE_BITS = 0x1f << 22`（bit 22-26：m_ahb/s_ahb/core/core2x/s0，L65/L272） | bit 22/23/24 + 26（L354-357/L400/L430） | **同一组位**（syna 是 pandora 的子集） |

**冲突机理**（两条驱动动作逐项相同）：
1. 都做 reset 时序：pandora L1546/L1548 与 L1607；syna `power_on()` L1499（先拉低）+ `tcm_reset()` L1509-1516（低 10 ms → 高 200 ms）
2. 都拉高 avdd 117：pandora L1612；syna L1502
3. 都把 GPIO 48-51 的 mux 设成 SPI function 1、6 mA：pandora `pt_gpio`；syna `use_engine_pins()` L1518-1525
4. 都各自 init GENI SE `0x1a80000`（改写 `SE_GENI_*` / DFS / DMA 寄存器）
5. 都读同一个 GPIO 158 做轮询

**若两者同时使能**（`pandora_touch=0xf` + `syna=1`，正是 klogY 的 cmdline）：后启动的一方会把芯片 reset 一遍并重置 SE，先启动的一方已建立的 TouchComm 会话（或 TCM 握手）被打断；更糟的是两个线程会同时读/写同一个 SE 的 FIFO，读到对方的数据。

**本次没打起来的原因**：`klogY`（mtime 00:41）对应的内核（推断 out39，23:55）里 `_sweet_ufs_init` 的 `bl` 序列**不含** `_popsicle_syna_init`——那时 syna 还没接线。out40（00:48）才加上，之后没有新日志，所以"两者同时使能会怎样"在实测中从未发生过。

### 3.4 pandora vs goodix —— **不冲突**

SE `0x1a80000` vs `0x1988000`、GPIO 48-51/158/66/117 vs 12-15/201/185/82、iovdd `L4I_E0` vs `L2F_E0` 全部不同。只共享 TLMM/GCC/RPMh 三个控制器基址，按不同位操作。可以同时使能。

### 3.5 sweet_touch 对任何一套的影响 —— **无（不参与编译）**

`TOUCH_SE_PA 0x00a84000`（SE7）与 fuxi 的 `0x00a90000`（SE4）同属 QUP1 wrapper 但不同 SE；GPIO 8/9/90 与 pandora/syna/goodix 的任何引脚都不重叠。但由于调用点不可达，这条路径在 PANDORA 构建里根本不生成代码。

### 4.4 事件流的真实性质（重要）

- 1,924 条 touch 事件（down 962 / up 962，**完全配对**）在**开机后 31.6 s 起、约 300 s 内**集中爆发，60 s 内就有 1,544 条
- 手指 id 0..9 **全用满**（10 个），与 `SWEET_TOUCH_FINGERS 10` 一致

### 5.4 结论

**队列是"活着的设备节点 + 空队列 + 无消费者"的纯死通道**：

1. `/dev/redwood-touch` 确实被创建（0666，全用户可读写），`touch_read` 里的 `msleep` 也在等
2. 但**没有任何代码打开它**——内核侧无，用户态在可查范围内无
3. 本次启动更彻底：`klogY` 用的内核没有 `bl _popsicle_syna_init` / `_popsicle_goodix_init`，所以**连生产者都没运行过**，队列里一条记录也没有（`redwood` 在 klogY 里 0 命中）
4. 代码自己知道这一点：`:111` 的注释就是 `/* nobody reads: drop the oldest */`
5. **它与 HID 事件链无关**——HID 走 `sweet_hid_touch` → `SweetHID.cpp`，`redwood_touch_post` 是另一条平行通路，只在 syna/goodix 里被调用，而这两条驱动都不碰 `sweet_hid_touch`（grep 均 0）

设计文档（`/mnt/d/ios/popsicle-port/gt9615-移植计划.md:34,128`、`syna-tcm-移植计划.md:291-302`）把这条队列写成"主副屏共用、靠坐标区分、SpringBoard 侧无需区分"——那是**计划**，实际是两端都空：驱动侧本次未接线，用户态侧未实现。

附带发现：`syna-tcm-移植计划.md:291-302` §5.5 声称"两个轮询线程…线程调度天然互斥，无需加锁"是错的——`redwood_input.c:106 touch_post` 内部确实持 `touch_lock`，加锁是对的。

## 附：本次审计的关键方法论更正

审计过程中出现过三处因搜索方法导致的误判，均已纠正：

1. **`SWEET TOUCH` 内核字符串"0 命中"** —— 用 `grep` 而非 `strings -a` 造成。实际内核里有 **27 条** `SWEET TOUCH: …` 字符串 → sweet_touch.c **编进内核了**，它的死因是"调用点编译期不可达"，不是"没编进去"。
2. **`PANDORA TOUCH: gcc before` / `pins before` 查不到** —— 内核里的模板是 `"PANDORA TOUCH: gcc %s: …"`（`pandora_touch.c:260`）与 `"pins %s:"`（`:240`），是 `%s` 参数化模板，用带参数值的整串去查必然 0 命中。不能据此判断内核与源码版本不一致。
3. **带 ` edge` 后缀的 HID 事件"0 条"** —— 锚点写 `edge$` 撞上 CRLF 行尾 `^M`。实际是 **50 条**（`grep -c 'edge'` 全文件 51，减去 1 条 `exec siriknowledged`）。

这三处都不影响最终结论，但值得记下来：**对不熟的内核字符串做存在性判断时，必须用 `strings -a` 并考虑 printf 模板的参数化形态。**
